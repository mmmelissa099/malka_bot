# TDD-0001: Bot de Atención Automatizada de Instagram - Cabaña Apícola Malka

## Contexto de Negocio (PRD)

### Objetivo
Automatizar la atención de mensajes directos de Instagram de Cabaña Apícola
Malka, respondiendo consultas frecuentes de clientes (diferencia entre celda
real y reina fecundada, envíos, precios, tiempos según temporada) sin
intervención manual, derivando a una persona real los casos que el sistema
no puede resolver con certeza.

### User Persona
- Nombre: Melissa (quién administra las redes / responde los DM hoy en el negocio)
- Necesidad: responder consultas de Instagram sin estar pendiente del
  celular todo el día, sin perder ventas por demoras, y sin que el bot
  invente información incorrecta sobre productos, genética o precios
  (un error acá tiene costo comercial real, no es solo un mal dato).

### Criterios de Aceptación
- El sistema debe responder preguntas frecuentes basándose únicamente en
  información real del negocio (RAG), sin inventar datos no presentes en
  los documentos indexados.
- El sistema no debe agregar comparaciones, garantías ni conclusiones que
  no estén explícitas en el contexto recuperado, aunque sean plausibles
  (descubierto empíricamente en la Semana 2: ver
  `docs/observaciones/semana2.md`).
- Las respuestas deben entregarse en texto plano, sin formato markdown
  (tablas, negrita, listas con sintaxis especial), dado que se envían
  directamente como mensajes de Instagram.
- El sistema debe mantener el contexto de la conversación dentro de una
  misma sesión (memoria).
- El sistema debe derivar a un humano cuando no tiene información
  suficiente para responder con certeza, en vez de arriesgar una respuesta.
- El sistema debe integrarse con la cuenta real de Instagram de Malka
  mediante la API de Meta (Standard Access, cuentas con rol de tester).
- TODO: definir un tiempo máximo de respuesta aceptable (ej: < 5 segundos).

## Diseño Técnico (RFC)

### Modelo de Datos

**FAQDocument** (documento indexado para RAG):
- `id`: identificador del chunk.
- `contenido`: texto de la FAQ.
- `categoria`: enum (`envios`, `precios`, `productos`, `genetica`).
- `embedding`: vector generado por el modelo de embeddings (no se persiste
  a mano, lo administra el vector store).

**ConversationState** (memoria de una conversación activa):
- `instagram_user_id`: identificador del remitente.
- `historial`: lista de `{rol, contenido, timestamp}`.
- `estado`: enum (`activa`, `escalada`, `cerrada`).

### Contrato de "API" (webhook de Meta, en vez de un endpoint propio)

- Endpoint receptor: `POST /webhook` (nuestro servidor, expuesto vía ngrok
  en desarrollo)
- Request body (formato real simplificado de Meta):
```json
{
  "entry": [{
    "messaging": [{
      "sender": { "id": "<instagram_user_id>" },
      "message": { "text": "<texto del mensaje>" }
    }]
  }]
}
```
- Respuesta: no se responde en el mismo request — se hace un `POST`
  aparte a la Instagram Messaging API con el texto generado por el
  agente, usando el Page Access Token.

### Stack tecnológico concreto 

- **Modelo de embeddings**: Google, `gemini-embedding-001`.
- **Vector store**: Chroma (local, sin infraestructura adicional —
  apropiado para ~15-20 documentos, no pensado para escala de
  producción).
- **LLM de chat**: `openai/gpt-oss-120b` servido por **Groq**.
  - Se empezó con Google Gemini (`gemini-2.5-flash`, luego
    `gemini-3.6-flash` tras una deprecación del primero). Se migró a
    Groq porque la capa gratuita de Gemini permite solo 20 llamadas al
    modelo de chat por día — insuficiente incluso para pruebas de
    desarrollo, y un riesgo real para la demo en vivo. Groq ofrece
    1.000 llamadas/día en su capa gratuita para este modelo.
  - Esto genera una **arquitectura de proveedor mixto**: embeddings en
    Google, chat en Groq. Es una decisión deliberada, no un
    descuido — cada proveedor se usa donde resuelve mejor su parte.
  - Hallazgo relevante: `gemini-3.6-flash` (y toda la familia Gemini
    3.x en adelante) ignora el parámetro `temperature` de forma
    permanente (decisión de Google, no un bug). Groq sí lo respeta,
    lo que permitió validar empíricamente el efecto de `temperature`
    sobre la consistencia de formato de salida (ver
    `docs/observaciones/semana2.md`).

### Componentes de Arquitectura (pipeline de LangChain)

1. **Retriever** : interfaz sobre el vector store (Chroma) que devuelve los documentos más      relevantes parauna consulta dada.
2. **Agente / Router** (equivalente al caso de uso): decide, según el mensaje entrante, si responder con RAG, usar el tool de catálogo, o escalar a un humano.
3. **Tools** (equivalentes a adaptadores de salida): funciones que consultan catálogo/stock y que marcan una conversación como escalada.
4. **Adaptador de entrada**: el webhook que recibe los eventos de Meta y se los pasa al agente.
5. **Memoria**: capa transversal que el agente consulta y actualiza en cada turno (no es un componente aislado, atraviesa todo el flujo).

## Casos de Borde y Errores

| Escenario | Resultado Esperado | Manejo |
|---|---|---|
| Pregunta fuera del dominio del negocio | El bot indica que no puede ayudar con eso | Restricción en el system prompt |
| El RAG no encuentra ningún documento relevante | Se escala a un humano en vez de inventar | Umbral mínimo de similitud en el retriever |
| Falla la llamada a la API del LLM | Reintento con backoff; si persiste, mensaje de error genérico | Try/except + logging |
| Se agota la cuota gratuita de la API del LLM (rate limit diario) | El sistema debe fallar de forma controlada, no silenciosa; se documenta como riesgo para la demo en vivo | Monitoreo de uso; plan de fallback a otro proveedor ya ejecutado una vez (Gemini → Groq) |
| El Page Access Token de Meta vence o se revoca | El webhook deja de poder responder | Monitoreo de expiración (ver TDD futuro de integración Meta) |
| Mensaje ambiguo sin contexto previo | El bot pide una aclaración en vez de asumir | Diseño del prompt + memoria de conversación |
| Cliente pide hablar con una persona explícitamente | Escalamiento inmediato, sin pasar por RAG | Detección de intención en el router |

## Plan de Implementación
1. Semana 1: chain básico (prompt + modelo + output parser).
2. Semana 2: RAG sobre FAQs del negocio (vector store Chroma).
3. Semana 3: memoria de conversación + tool de catálogo/stock.
4. Semana 4: agente completo (router) que decide entre RAG, tool y escalamiento.
5. Semana 5: integración real con la API de Instagram (webhook) + demo en vivo.
